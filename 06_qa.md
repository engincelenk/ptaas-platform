## 1. Teststrategie

### Testing-Pyramide

```
        /\
       /  \
      / E2E \        → Playwright (5-10 kritische User Flows)
     /--------\
    / Integration\   → Supertest + Test-DB (API Controller Tests)
   /------------\
  /  Unit Tests  \   → Jest (Services, Utils, Scanner-Checks)
 /________________\
```

**Philosophie:**
- Unit Tests: schnell, viele, isoliert — testen Business Logic
- Integration Tests: testen API-Verhalten mit echter DB (Test-Container)
- E2E Tests: testen kritische User Flows aus Nutzerperspektive
- Kein "Test um des Tests willen" — jeder Test soll echte Bugs finden

## 2. Backend Testing (NestJS / Jest)

### Unit Tests — Services

```typescript
// scans/scans.service.spec.ts
describe('ScansService', () => {
  describe('createScan', () => {
    it('should enqueue scan job and emit WebSocket event', async () => {
      const mockScan = { id: 'scan-1', tenantId: 'tenant-1' };
      prisma.scan.create.mockResolvedValue(mockScan);
      
      await service.createScan('project-1', createScanDto, 'tenant-1');
      
      expect(scanQueue.add).toHaveBeenCalledWith('execute-scan', 
        expect.objectContaining({ scanId: 'scan-1' }));
      expect(scanGateway.emitToTenant).toHaveBeenCalledWith(
        'tenant-1', 'scan:queued', { scanId: 'scan-1' });
    });

    it('should reject scan if target not in project scope', async () => {
      await expect(
        service.createScan('project-1', { targets: ['192.168.1.1'] }, 'tenant-1')
      ).rejects.toThrow(ForbiddenException);
    });
  });
});
```

### Integration Tests — Controller + DB

```typescript
// scans/scans.controller.integration.spec.ts
describe('ScansController (integration)', () => {
  let app: INestApplication;

      imports: [AppModule],

    await app.init();
  });

  it('POST /projects/:id/scans should return 201', async () => {

      .post(`/api/v1/projects/${testProjectId}/scans`)

      .send({ type: 'WEB_ONLY', targets: ['https://example.com'] });

      .get(`/api/v1/projects/${otherTenantProjectId}/findings`)
      .set('Authorization', `Bearer ${testJwt}`);
    
    expect(response.status).toBe(404);  // Nicht 403 — kein Info-Leak
  });
});
```

## 4. Scanner Testing (pytest)

```python
# tests/test_web_security_worker.py
import pytest
import httpx
from respx import MockRouter
from workers.web_security.checks import check_security_headers

@pytest.fixture
def mock_router():
    with MockRouter() as router:
        yield router

async def test_detects_missing_hsts(mock_router):
    mock_router.get("https://example.com").mock(
        return_value=httpx.Response(200, headers={})
    )
    async with httpx.AsyncClient() as client:
        findings = await check_security_headers(client, "https://example.com")
    
    hsts_finding = next(f for f in findings if "Strict-Transport-Security" in f.title)
    assert hsts_finding.severity == "HIGH"

async def test_no_finding_when_headers_present(mock_router):
    mock_router.get("https://secure.com").mock(
        return_value=httpx.Response(200, headers={
            "Strict-Transport-Security": "max-age=31536000",
            "X-Frame-Options": "DENY",
            "X-Content-Type-Options": "nosniff",
            "Content-Security-Policy": "default-src 'self'",
        })
    )
    async with httpx.AsyncClient() as client:
        findings = await check_security_headers(client, "https://secure.com")
    
    assert len(findings) == 0
```

## 5. Kritische Testfälle

### Security-kritisch (alle müssen bestehen vor Launch)

| # | Testfall | Erwartetes Ergebnis |
|---|---------|-------------------|
| S-01 | Tenant A greift auf Findings von Tenant B zu | 404 (kein Data Leak) |
| S-02 | JWT ohne tenantId wird abgelehnt | 403 |
| S-03 | Scan-Target ist private IP (192.168.x.x) | 403 Forbidden |
| S-04 | Rate Limit: 101 Requests in 15 Min | 429 Too Many Requests |
| S-05 | Scanner-Worker greift interne API ohne Auth an | 401 |
| S-06 | RBAC: VIEWER versucht Scan zu starten | 403 |
| S-07 | SQL Injection in Finding-Filter | 400, kein DB-Error |
| S-08 | XSS in Projekt-Name | Escaped in UI |

### Funktional-kritisch

| # | Testfall | Erwartetes Ergebnis |
|---|---------|-------------------|
| F-01 | Scan wird gestartet und läuft durch | Status: COMPLETED |
| F-02 | Scan schlägt fehl (Timeout) | Status: FAILED, Error-Message |
| F-03 | Mehrere gleichzeitige Scans (Queue) | Alle werden abgearbeitet |
| F-04 | PDF-Report wird korrekt generiert | PDF mit allen Findings |
| F-05 | Finding-Status wird auf FIXED gesetzt | Status in DB aktualisiert |
| F-06 | WebSocket: Scan-Status-Update in Echtzeit | Event "scan:completed" empfangen |
| F-07 | Report-Download: nur eigener Tenant | S3-URL valide für 15 Min |

## 6. Testautomatisierung im CI/CD

```yaml
# .github/workflows/test.yml
jobs:
  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - run: npm run test:unit -- --coverage --coverageThreshold='{"global":{"lines":80}}'

  integration-tests:
    services:
      postgres: { image: postgres:16 }
      redis: { image: redis:7 }
    steps:
      - run: npm run test:integration

  e2e-tests:
    if: github.ref == 'refs/heads/main'
    steps:
      - run: npx playwright test --reporter=html

  scanner-tests:
    steps:
      - run: cd apps/scanner && pytest --cov=workers --cov-fail-under=75
```

## 8. Definition of Done

Ein Feature gilt als **fertig** wenn:

- [ ] Unit Tests geschrieben und bestehen (Coverage ≥ 80%)
- [ ] Integration Test für API-Endpunkt existiert
- [ ] Kein ESLint / TypeScript Fehler
- [ ] Security-Tests für den Feature-Scope bestehen (S-0x)
- [ ] Kein bekannter CRITICAL/HIGH Bug offen
- [ ] Code Review durch zweiten Entwickler
- [ ] Feature läuft in Staging-Umgebung
- [ ] Acceptance Criteria aus User Story erfüllt
- [ ] Audit Logging implementiert (falls schreibende Aktion)
- [ ] API Dokumentation aktualisiert (Swagger)
